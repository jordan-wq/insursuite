## 3. Two partner agents did overnight research (read-only, no code touched)

You said I could "hire a partner to think with" — I ran two, one on UX/design, one on product/business/risk, both grounded in actually reading the codebase rather than generic advice. Full reports are in the conversation transcript above; here's the synthesis.

### The one thing I'd fix before anything else

The product-partner agent found a real, verified bug — I checked the code myself, it's real:

**`saveProfilePatch` (`app/page.tsx:924`) silently destroys profile data on concurrent edits.** It merges a patch into a client-held snapshot of the profile, then `POST /api/client-profile` does a full-column replace — not a server-side merge, no version check. If a client has Settings open while a staff member edits the same client via Call Intake (or two browser tabs, or two staff members), whichever save lands second **silently wins and erases everything the other one wrote**. No error, no trace. This gets worse the moment the onboarding flow above ships, since it's a second system touching the same profile data.

I did not fix this — it's a real design decision (server-side merge? optimistic concurrency with a version column? something else?), not a one-line patch, and not something to change unsupervised on your data model overnight.

### Also confirmed real (I verified each of these myself, not just trusting the agent)

- **"Call Intake" is live in the client's own nav today** (`app/page.tsx:131`) — not one of the three deliberately-hidden features. A client can open a tab and see whatever health notes, medications, nicotine-use, and driving-history answers staff have recorded about them, because `GET /api/client-profile` returns the whole `profile` blob unfiltered. This is exactly the kind of exposure the new underwriting spec deliberately designed around (RLS-locked table, zero client policies) — worth deciding whether to pull this tab from client nav now, independent of when the new flow ships.
- **CLAUDE.md was pointing at a security guard that no longer exists** — `isAssignedToAgent()`, described as "the IDOR guard this codebase relies on," was actually removed during tonight's admin-console-shell work (a deliberate, spec-approved widening to the flat isAgent-only model). I fixed the doc (see the `CLAUDE.md` diff) since a stale claim like that could mislead a future security review into thinking a guard exists that doesn't. This is the only content edit I made outside the two new doc files — happy to revert if you'd rather do it yourself.
- The PDF-extraction worker loads from `unpkg.com` at runtime with no integrity hash, in the same page that handles client documents — and is called out as the actual reason CSP work keeps stalling (a strict `script-src` would break it). Self-hosting it from `/public` is a small, contained fix that unblocks the CSP work already on your list.
- `user_policies` has no `status` column — every policy renders as hardcoded "Active" forever. No lapse/renewal tracking exists anywhere in the schema.

### Ranked recommendations (both agents' full reasoning is in the transcript)

1. **Fix the profile lost-update bug, and reconsider Call Intake's client-nav visibility** — cheap, and both current-flaw fixes needed before more health-data surfaces get built on top.
2. **Policy lifecycle** — a real `status` column, renewal/lapse tracking, an "at risk" queue in the staff console.
